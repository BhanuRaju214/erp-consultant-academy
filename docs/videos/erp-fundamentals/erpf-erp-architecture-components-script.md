# Video script: ERP Architecture and Major Components

ERP Fundamentals lesson video (/videos/erpf-erp-architecture-components.mp4), shown at the top of the lesson. Built from the lesson content; Odoo colours, nexusEPM logo, narration by Microsoft neural voice Neerja (Indian English) with captions.

| # | On screen | Narration |
|---|---|---|
| 1 | Title card: **ERP Architecture and Major Components**. The layers behind the screens, and why one shared database changes everything. | Welcome to lesson four. In this video you will learn how an ERP is put together, layer by layer, and the one distinction that saves consultants hours of confused support calls: configuration, master data and transactions. |
| 2 | Step ?: **Will the accountant see it?** (who, Odoo menu, impact) with an animated **Customer · payment terms** card | The finance director of Vertex Build Contractors, a fictional company, asks a simple question. If I change a customer's payment terms in the sales screen, will the accountant see it? To answer confidently, you need to understand how an ERP is built. A techno functional consultant does not need to be a system architect, but must understand the layers well enough to explain behaviour, diagnose issues and talk to developers. |
| 3 | **How an ERP is put together**. Animated flow: User interface ▸ Application server ▸ Integration layer ▸ Database ▸ Reporting | Think of an ERP as layers. At the top, the user interface: a web browser, a mobile app or a point of sale terminal. Below it, the application server, where the modules, business rules, workflows and security run. The integration layer lets banks, couriers and online stores connect. At the bottom is one database holding shared master data and transactions. Reporting reads that same data. Because every module uses the same database, a change made in Sales is visible to Accounting immediately. |
| 4 | **Modules, server and database**. Cards: Modules (apps) · Application server · Relational database | Modules, which Odoo calls apps, each cover one business area. They can be installed independently, but their value comes from working together. Installing Sales and Inventory, for example, links sales orders to deliveries automatically. The application server holds the business logic: what happens when an order is confirmed, which accounts a bill posts to, and who may approve what. It also enforces security. And the relational database, PostgreSQL in Odoo's case, lets one report combine sales, stock and accounting without exports. |
| 5 | **Interface, integration and reporting**. Cards: User interface · Integration layer · Reporting | The user interface should hide complexity, and a big part of the consultant's job is making sure each role sees only what it needs. The integration layer connects external systems through A P Is, file imports or ready made connectors, for bank statement feeds, payment gateways, courier tracking and e-invoicing portals. Reporting covers operational reports like stock on hand, financial reports like the balance sheet, and analytical views such as pivot tables and dashboards. |
| 6 | Shared master data | Shared master data is the backbone of integration. A customer record is used by CRM, Sales, Accounting and Helpdesk. A product is used by Sales, Purchase, Inventory, Manufacturing and point of sale. The chart of accounts is used by every module that posts entries. Because everyone reads the same record, there is nothing to re-type and nothing to reconcile. In Odoo, customers and vendors are both stored as contacts, so the same record can be both. |
| 7 | Configuration vs master data vs transactions | Now the most important distinction. Configuration, such as tax rates, warehouse setup and approval rules, is set during implementation and changes rarely. Master data, such as customers and products, changes occasionally. Transactions, such as orders, invoices and payments, are created constantly. Mixing these up is a classic beginner mistake. A wrong configuration affects every future transaction, while a wrong transaction affects only itself. |
| 8 | Step ✓: **The answer: master data, not history** (who, Odoo menu, impact) with an animated **Customer · Vertex client** card | So back to Vertex Build Contractors. Payment terms are stored on the customer master record, which both Sales and Accounting read. When the salesperson changes the terms from thirty to forty five days, the next quotation and the next invoice both use forty five. But invoices already posted keep their original thirty days. They are transactions, and changing master data does not rewrite history. Explaining this clearly prevents a lot of confused support calls. |
| 9 | **Key takeaways**. Cards: Layers · Master data integrates · One database · Three kinds of data | To recap. An ERP has layers: user interface, application server with modules, logic and security, integration, database and reporting. Shared master data is what makes modules integrated, and one database lets reports combine data across departments. Always distinguish configuration, master data and transactions, because they behave differently. Now open the lesson and try the exercises: decide what happens to Vertex's posted invoices, and spot which item is configuration. |
