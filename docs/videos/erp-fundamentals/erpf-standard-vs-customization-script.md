# Video script: Standard ERP vs Customization

ERP Fundamentals lesson video (/videos/erpf-standard-vs-customization.mp4), shown at the top of the lesson. Built from the lesson content; Odoo colours, nexusEPM logo, narration by Microsoft neural voice Neerja (Indian English) with captions.

| # | On screen | Narration |
|---|---|---|
| 1 | Title card: **Standard ERP vs Customization**. When to configure, when to customize, and when to change the process instead. | Welcome to lesson eight of E R P Fundamentals. In this video you will learn the most important judgement a consultant makes: when to configure the system, when to customize it, and when to change the business process instead. |
| 2 | 140 changes vs 6 changes | Let us compare two companies. Granite and Co Construction asked for one hundred and forty changes during their project: custom screens, renamed fields, new approval steps and special reports. Two years later, an upgrade was quoted at almost the cost of the original implementation, because every change had to be re-tested and many rewritten. Oakridge Distributors adapted its processes to the standard system, kept just six customizations, and upgraded in three weeks. |
| 3 | **Configuration, customization, extension**. Cards: Configuration · Customization · Extension / integration | There are three levels of adaptation. Configuration uses built-in settings with no code, like enabling multiple warehouses, defining taxes or setting payment terms; a functional consultant does this. Customization changes or adds behaviour with code or low-code tools, such as a new field with logic on sales orders. Extension or integration adds capability alongside the core, for example a connector to a courier's system or a custom module for equipment rental. |
| 4 | **Low-code is still customization**. Cards: Odoo Studio · Same lifecycle cost | Some vendors offer low-code tools. In Odoo, the Studio app, available only in Enterprise, lets users add fields, change views and create simple automations without writing Python. But do not be fooled. Because it changes behaviour and the data model, it is still a customization, and it must be documented, tested and maintained just like code. |
| 5 | **Five questions before any customization**. Animated flow: Standard? ▸ Configure? ▸ Change process? ▸ Existing module? ▸ Custom build | Before agreeing to any customization, walk up this ladder. First, does standard already do it? Many gaps are just features the client has not seen yet. Second, can configuration achieve it? Third, can the process change, because the client's way may be familiar rather than better? Fourth, is there a ready-made, well supported module? Only then, custom development, with a written specification and a cost benefit justification. |
| 6 | **The long-term cost of customization**. Cards: Upgrade cost · Testing cost · Dependency risk · Performance · Lost innovation | Why is custom code the last rung? Because its cost continues for the life of the system. Each new version may change the code a customization depends on, and every customization must be re-tested on every upgrade. Knowledge sits with the developer who wrote it. Poor code can slow down or break standard features. And heavily modified systems often skip upgrades altogether, missing new standard features. Over time, the effort gap between a customised and a standard system keeps widening. |
| 7 | **Good reasons to customize**. Cards: Competitive advantage · Legal requirement · High-volume automation · Essential integration | Customization is not always wrong. Good reasons include a genuine competitive advantage the standard cannot support, a legal or regulatory requirement not covered by standard or localisation modules, a high-volume process where automation saves a lot of time every day, and an integration with an essential external system. |
| 8 | Classify every requirement | During requirement analysis, label every requirement as standard, configuration, customization, integration or reporting. Look at Oakridge's requests. Entering order lines by typing product codes turned out to be standard. Thirty day payment terms is configuration. A pallet label in a major customer's format needs a customization. Booking shipments with the courier's system is an integration, and monthly margin by category is a reporting need. This classification drives effort estimates and the fit gap analysis. |
| 9 | Step Tip: **The order-entry screen that was never built** (who, Odoo menu, impact) with an animated **Requirement log · Oakridge** card | Here is the consultant tip. Oakridge wanted a custom screen to enter orders quickly by product code. Instead of building it, the consultant demonstrated that standard sales order lines already accept product codes, and that keyboard entry was fast enough after short training. The request was closed as standard, training. The pallet label had no standard equivalent, so it was approved as a small customization with a written specification. Always demonstrate before you build. |
| 10 | **Key takeaways**. Cards: Know the three levels · Climb the ladder · Customization costs forever · Classify every requirement | To sum up. Configuration uses built-in options, customization changes behaviour, and extension adds capability. Climb the standard first ladder before agreeing to any development. Remember that every customization, including low-code changes in Studio, adds upgrade, testing and maintenance cost for the life of the system. And classify every requirement. Now try the exercises in this lesson, starting with putting the ladder in order and classifying Oakridge's requests. |
