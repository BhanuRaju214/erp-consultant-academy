# Video script: SaaS, Hosting, Environments, Databases and User Access

ERP Fundamentals lesson video (/videos/erpf-saas-hosting-environments-access.mp4), shown at the top of the lesson. Built from the lesson content; Odoo colours, nexusEPM logo, narration by Microsoft neural voice Neerja (Indian English) with captions.

| # | On screen | Narration |
|---|---|---|
| 1 | Title card: **SaaS, Hosting, Environments, Databases and User Access**. Why professionals never experiment in production, and how access is kept under control. | Welcome to lesson seven of E R P Fundamentals. Whether your E R P runs as software as a service or on your own hosting, the same discipline applies. In this video you will learn why projects use separate environments, how databases are organised, and how user access is controlled so that one careless change cannot damage live business. |
| 2 | Step !: **A tax test in the live database** (who, Odoo menu, impact) with an animated **Customer invoices** card | Here is the story behind this lesson. Two weeks before go-live at Meridian Wholesale Foods, a junior consultant tested a new tax setting directly in the live database. Every invoice issued that afternoon used the wrong tax rate, and each one had to be credited and issued again. The lesson is simple: never experiment in production. |
| 3 | The four environments | An environment is a separate copy of the E R P used for one purpose. Developers build in development with small sample data. Consultants and testers check functions and integrations in test. Key users rehearse in staging, which holds a copy of production, for user acceptance testing and migration dry runs. And production is where the real business runs on real data, so nobody tries things there. |
| 4 | **The promotion path**. Animated flow: Development ▸ Test ▸ Staging ▸ Production | Changes travel one way along the promotion path: development, then test, then staging, and only then production. Each step is a gate, so a change reaches live users only after it has passed its checks. Data travels the other way. Production is copied back to staging, often anonymised, so that tests reflect real life. |
| 5 | **How changes reach production**. Cards: Code · Configuration | Code and configuration reach production in different ways. Custom modules are promoted through version control and a deployment. But settings made on screen, such as taxes and journals, are stored as data inside the database. They must be re-applied in production from a documented configuration workbook, or carried over in a prepared database. That is why good consultants record every setting they change. |
| 6 | **Databases, companies and backups**. Cards: Databases · Multi-company · Backups | An E R P instance can host one or several databases, and each one is a completely separate world of companies, users and data. One database can also hold several companies that share master data but keep separate accounting. Choosing between one database with several companies and separate databases is an early decision, because inter-company transactions and consolidated reporting are much easier in one database. And remember: an untested backup is not a backup. |
| 7 | **Principles of user access**. Cards: Named users · Groups and roles · Least privilege · Segregation of duties | Now user access. Every person gets their own named user, because shared logins destroy the audit trail and usually breach licence terms. Access is granted through groups or roles, not person by person. Record rules can go further and limit which records a user sees, such as only their own customers. Apply least privilege, so each user has only what the job needs. And segregate duties: the person who creates a vendor should never approve payments to that vendor. |
| 8 | A simple access matrix | Here is a simple access matrix. A salesperson sees only their own sales documents, while the sales manager sees all of them and can read invoices. The storekeeper is a full user of inventory, and the accountant has full rights in accounting but only reads the other apps. Only the system administrator holds admin rights everywhere, and that should be a very small group of people. |
| 9 | **Four rules after the tax incident**. Cards: Staging first · Two admins · Monthly refresh · Quarterly restore | After the incident, Meridian adopted four rules. Every configuration change is tried in staging first and recorded in the configuration workbook. Only two named administrators can change settings in production. Staging is refreshed from production every month, with personal data anonymised. And backups are restored to a test server every quarter. Support tickets about mysterious setting changes dropped to zero. A common mistake to avoid: giving someone admin rights temporarily just to get past an error. |
| 10 | **Key takeaways**. Cards: Never experiment in production · Code forward, data backward · Decide database design early · Control access | To sum up. Never experiment in production; use separate development, test, staging and production environments. Code moves forward, production data moves backward, and on-screen configuration must be documented. Decide early between one database with several companies or separate databases. And control access with groups, least privilege and segregation of duties, and prove your backups by restoring them. Now try the exercises in this lesson, starting with matching each activity to the right environment. |
