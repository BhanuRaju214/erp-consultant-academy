# Video script: Phase 6 — Development and Integration

Narrated lesson video for ERP Implementation Methodology. Video file: public/videos/impl-phase-6-development-integration.mp4. Voice: en-IN-NeerjaNeural.

| # | On screen | Narration |
|---|---|---|
| 1 | Title card: **Phase 6 — Development and Integration**. Turn approved gaps into clear specifications, so the developer builds the right thing, once. | Welcome to lesson seven of Implementation Methodology. In this video you will learn how a techno-functional consultant turns approved gaps into technical specifications, designs integrations, and verifies the build before user testing begins. |
| 2 | **Three approved gaps**. Cards: Pallet label · EDI order import · Expiry warning | Lakeside Fresh Foods, a fictional food company, needs three things the standard system does not provide. A pallet label in a retailer's format, an automatic order import from a retail chain's E D I provider, and an expiry date warning on delivery screens. Each gap was approved in the fit-gap analysis. Now the consultant's job is to specify each one so clearly that the developer builds the right thing, once. |
| 3 | **Every build traces to an approved gap**. Animated flow: Approved gap ▸ Functional spec ▸ Technical spec ▸ Estimate & approval ▸ Build in DEV ▸ Unit test, review, TEST ▸ Promote to STAGING | The path always starts with an approved gap and its requirement I D. The functional specification explains what is needed and why, and the technical specification explains how. After an estimate is approved, the developer builds in the development environment under version control. Then come unit tests, code review, deployment to the test environment, functional and integration testing, defect fixes, and finally promotion to staging. |
| 4 | **Build without guessing, test without asking**. Cards: References · Data model · Business logic · Security · Upgrade impact · Tests & acceptance | A good specification lets a developer build without guessing, and lets a tester verify without asking. It references the requirement and fit-gap I Ds, then describes the data model, the business logic, security, any reports or integration, and the upgrade impact. Crucially, it ends with test scenarios and measurable acceptance criteria, because those are what the process owner will sign against. |
| 5 | Rules a tester can verify | Here is the business logic section for the expiry warning. If a lot expires within ten days of the scheduled delivery, the user sees a warning but can still validate. If the lot expires before the delivery date, validation is blocked with a clear message. And if the product is not tracked by lot, there is no check at all. Each rule is precise enough to become its own test. |
| 6 | **Extend, never modify, standard**. Cards: Separate modules · Version control · No direct database edits · Configuration in the module | Expect good developers to put custom code in separate modules that extend standard code rather than modify it, because modified standard code breaks on upgrade. Code lives in version control, such as Git, and is reviewed before it is merged. Nobody edits the production database directly. And configuration data ships inside the module where possible, so every environment stays consistent. |
| 7 | Seven questions for every integration | Integrations connect the E R P to e-commerce, banks, couriers, payroll or E D I providers, often through the external A P I or middleware. Design each one by answering a few questions. Which direction does data flow, and how often? Which system is master of the data, and what key matches records? How are errors handled and retried? And which minimal-rights integration user runs it, at what volume? |
| 8 | Step Line 3: **Flagged, not dropped** (who, Odoo menu, impact) with an animated **EDI order import** card | During integration testing at Lakeside, the retail chain sent a product code that did not exist. Because the specification required unmatched lines to be logged and flagged rather than dropped, middleware alerted I T support, and the line was kept for review. A code mapping table was added before user acceptance testing. Without that error handling rule, the order line would simply have vanished. |
| 9 | **Three layers of proof**. Cards: Unit tests · Integration tests · Functional verification | Before user acceptance testing, the developer unit tests each rule in isolation. Integration tests check data flows end to end, including failures like a wrong product code, a duplicate order or a network timeout. Then the consultant verifies the result in the test environment against the specification's acceptance criteria. |
| 10 | Step RTM: **No approval, no build** (who, Odoo menu, impact) with an animated **Pallet-label report** card | A common mistake: a developer offers to start the pallet label report before the fit-gap decision is approved, just to save time. Say no. Unapproved builds become unbillable rework or scope creep. Also watch for vague specs like make it like the old system, and integration users with administrator rights. |
| 11 | **Key takeaways**. Cards: Approved gaps only · Complete specs · Extend standard · Design integrations | To sum up. Only approved gaps become development, each traced to a requirement I D. Specifications cover data, logic, security, integration, upgrade impact, tests and acceptance. Extend standard through separate modules under version control, design integrations carefully, and test before handing over. Now try the exercises in this lesson, starting with the developer's offer to build early. |
