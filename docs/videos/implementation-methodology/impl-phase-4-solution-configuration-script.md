# Video script: Phase 4 — Solution Configuration

Narrated lesson video for ERP Implementation Methodology. Video file: public/videos/impl-phase-4-solution-configuration.mp4. Voice: en-IN-NeerjaNeural.

| # | On screen | Narration |
|---|---|---|
| 1 | Title card: **Phase 4 — Solution Configuration**. Turning a signed design into a working, documented system. | Welcome to lesson five. In this video you will learn how to turn a signed to-be design into a working system, in the right order, in a test environment first, and with every setting recorded in a configuration workbook. |
| 2 | Step 45: **Design signed — now build it** (who, Odoo menu, impact) with an animated **Rework risks** card | Riverbend Distributors, a fictional company, has a trading company and a service company, three warehouses and forty five users. The to-be design is signed off, and the consultant now turns it into a working system. Configuration done in the wrong order, or without documentation, causes rework. For example, products created before units of measure are final, or journals created before the chart of accounts has been reviewed. |
| 3 | **Build it exactly as designed**. Cards: Test environment first · Configuration workbook · Validate with key users | Configuration has three objectives. Build the system exactly as designed, in a test or configuration environment first. Record every setting in a configuration workbook, so it can be reproduced in production and supported later. And validate each configuration with key users, so problems are caught before any data is loaded. |
| 4 | **Each area builds on the one before**. Animated flow: Company & localisation ▸ Users & access ▸ Accounting foundations ▸ Inventory structure ▸ Products & UoM ▸ Sales / purchase ▸ Automation & reports | Configure in a logical order. Start with the company and fiscal localisation, then users and access. Next come accounting foundations: the chart of accounts, taxes, journals and payment terms. Then the inventory structure, with warehouses, locations and routes, followed by products and units of measure. After that, sales and purchase settings, sequences, automation, approvals and reports. The order matters because products need units, taxes and warehouses, and automation needs documents and roles to exist. |
| 5 | **Foundations to get right**. Cards: Companies and branches · Users and record rules · Warehouses · Localisation, taxes, journals | A few areas deserve special care. First decide whether branches are separate companies with separate accounting, or warehouses and analytic accounts within one company. Define user roles from the to-be design, not from people's names, and test each role by logging in as a sample user. Choose one, two or three step reception and delivery per warehouse. And review the fiscal localisation package for accounts and taxes, rather than recreating them by hand. |
| 6 | **Details that are hard to change later**. Cards: Units of measure · Sequences · Automation and Studio · Reports | Units of measure need categories and ratios, for example a box of one point four four square metres, and purchase and sale units must sit in the same category as the stock unit. Invoice numbering often has legal requirements, so verify local rules before changing it. Use standard settings like purchase approval thresholds first. Studio, an Enterprise-only tool, adds no-code fields and automation, but treat those as customizations and record them. |
| 7 | The configuration workbook | The workbook is a core deliverable, not optional paperwork. Each row records the setting, the value or decision, the requirement and design it comes from, who configured it, when, in which environment, and who verified it. Why does that matter? Most settings made in the user interface live in the database and do not travel with code. The workbook is how you rebuild test in production, and how support understands every setting later. |
| 8 | Do and don't | Here is the discipline in short. Configure and verify in test first, and log every setting with its requirement number. Never configure directly in production, and never give everyone administrator rights temporarily, because temporary access tends to stay. Wrong unit of measure categories or tax setup discovered after transactions exist become very hard to change, so get them right before any data arrives. |
| 9 | Step 1: **Branches: one company, not three** (who, Odoo menu, impact) with an animated **Company structure** card | At Riverbend, the consultant first set up the branches as separate companies. During a configuration walkthrough, finance explained that the branches share one tax registration and one set of books. So the design changed to one company with three warehouses and analytic accounts per branch. It was caught early, before data loading, only because the workbook was reviewed with the client. |
| 10 | **Key takeaways**. Cards: Configure in order · Test before production · Workbook is core · Test every role | To sum up. Configure in a logical order, from company and access through accounting, inventory and products, to automation and reports. Always configure and verify in test before production. Keep the configuration workbook complete, because it is a core deliverable. Use standard and localisation features first, and test access by logging in as each role. Now try the exercises in this lesson, starting with putting Riverbend's configuration areas in the right order. |
