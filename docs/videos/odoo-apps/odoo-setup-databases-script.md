# Video script: Setting up Odoo, databases and apps

Narrated overview video for the course Odoo Setup: Installation, Databases & Apps. Video file: public/videos/odoo-setup-databases.mp4. Voice: en-IN-NeerjaNeural.

| # | On screen | Narration |
|---|---|---|
| 1 | Title card: **Setting up Odoo, databases and apps** | Welcome to Odoo Application Training. Before you configure a single app, you need a running Odoo, a safe set of databases, and the right apps installed. In this video you will learn how to choose an edition and a hosting option, install Odoo, manage databases with the database manager, and install apps without breaking anything. |
| 2 | Four decisions: **Four decisions to make with the client** | Every Odoo project starts with four decisions, made with the client before the first configuration workshop. First, the edition: Community or Enterprise. Second, where Odoo will run: Odoo Online, Odoo dot S H, or the client's own server. Third, the version, which is usually the latest stable major release. And fourth, how many databases you need, and who may touch each one. Wrong answers here are expensive later. |
| 3 | Editions: **Community vs Enterprise** | Odoo is open core: one code base, two editions. Community is free under the L G P L licence, and already includes CRM, Sales, Purchase, Inventory and Manufacturing. Enterprise is paid per user. It adds the full Accounting app with bank synchronisation, where Community has Invoicing only. It also adds Studio, Sign, Planning, Quality and many more apps, plus official support and Odoo's upgrade service. Community can only be self-hosted. Enterprise can run on Odoo Online, Odoo dot S H, or on-premise. |
| 4 | Hosting: **Three ways to host Odoo** | Odoo Online is software as a service. Odoo runs everything, and you can start in minutes, but only standard apps and Studio are allowed. No custom Python modules. Odoo dot S H is Odoo's cloud platform for Enterprise with your own code. Each project has production, staging and development branches, with automatic backups. On-premise means your own server, with Community or Enterprise. You get full control, but you also own security, backups, monitoring and upgrades. Our training company, Northwind Office Supplies, needs a custom integration with a courier's A P I. That rules out Odoo Online, so the recommendation is Odoo dot S H. |
| 5 | Installing: **Install Odoo locally** | For a quick demo, start a free trial on odoo dot com. For learning and prototypes, install Odoo on your own machine. The fastest way is Docker. Odoo needs a PostgreSQL database server, so you run two containers: one for PostgreSQL and one for Odoo, published on port eight zero six nine. On a Linux server, most installations are done from source. Install PostgreSQL, clone the Odoo seventeen branch from GitHub, install the Python requirements, and add wkhtmltopdf so reports print as PDF. Then start odoo-bin with the addons path, and open localhost, port eight zero six nine, in your browser. |
| 6 | Configuration: **Settings every consultant should recognise** | Server options live in a configuration file, usually called odoo dot conf. You don't need to memorise them all, but you must recognise a few. The admin password is the master password that protects the database manager. Make it long, random and stored in a vault. The database settings tell Odoo how to reach PostgreSQL, and the addons path lists the folders that contain standard, Enterprise and custom modules. The data directory holds the filestore, where attachments are kept. In production, set list D B to false to hide the database manager, put Odoo behind an HTTPS proxy, and run several workers so one heavy report doesn't block everyone else. |
| 7 | What a database is: **PostgreSQL data + filestore** | An Odoo database holds one complete business: companies, users, installed apps, settings, master data and every transaction. It has two parts that always travel together. The PostgreSQL database, and the filestore, where attachments, images and P D Fs are stored. That's why a plain PostgreSQL dump is not a full backup: it misses the attachments. One Odoo server can host many databases, for example production, staging and training. Each one is completely separate. |
| 8 | Create a database: **The database manager** | On a self-hosted Odoo, databases are managed at slash web slash database slash manager. Every action asks for the master password. To create a database, enter a name. Use a convention such as client dash environment, for example northwind dash training. The email and password become the first administrator login. Choose the language and the country carefully. The country decides the currency and, once Accounting is installed, the chart of accounts and taxes. Tick demo data only for training databases. It fills the database with sample customers, products and orders, and it never belongs in production. |
| 9 | Manage databases: **Duplicate, back up, restore, delete** | Next to each database you'll find the everyday actions. Duplicate copies a database and its filestore under a new name, perfect for trying a risky change on today's data. Backup downloads a zip file with both the data and the filestore. Take one before upgrades, mass imports and go-live. Restore uploads a backup as a new database. Odoo asks whether it was moved or copied. Choose copy for every test database, so it gets a new identity and isn't confused with production. Delete is permanent, so use it only for old test copies. And remember: a backup you've never restored is only a hope. Test a restore before go-live. |
| 10 | Environments: **Changes move up, data moves down** | A safe project uses one database per purpose. Developers and consultants build and break things in development. Staging is a recent copy of production, used for user acceptance testing and go-live rehearsals. Production is the real business, and only tested changes reach it, in a planned window, right after a fresh backup. And end users train in a separate training database, never in production. Changes always travel from development to staging to production, while data is copied down from production to staging. |
| 11 | Neutralization: **Neutralize every copy of production** | A copy of production still contains live mail servers, payment keys and scheduled jobs. On one real project, three hundred and forty customers received a test invoice from a copy. Neutralizing a database switches all of that off. Mail servers are disabled, and scheduled actions are stopped. Payment providers go into test mode, and bank synchronisation and other external connections are cut. Odoo dot S H neutralizes staging branches automatically. On-premise, tick Neutralize when you duplicate or restore the database, before anyone logs in. |
| 12 | Apps: **Installing one app installs its dependencies** | Everything in Odoo is a module, and an app is simply a main module with its own icon on the home screen. Open the Apps menu, search for the app, and click Activate. Odoo installs the app and everything it depends on. For example, installing Sales also installs Contacts, Product, Invoicing, Discuss and Sales Teams. Some features are installed from Settings instead. Ticking lots and serial numbers in Inventory installs its module. Turn on developer mode to see Update Apps List, which finds newly added custom modules, and the Upgrade button for modules whose code has changed. |
| 13 | Uninstall with care: **Uninstalling deletes data** | Uninstalling is the dangerous direction. It removes the app's models and data, together with every module that depends on it, and there is no undo except a backup. So install only the apps in scope, try any uninstall on a duplicate first, and back up before installing custom modules in production. If a user simply shouldn't see a menu, use access rights. Never uninstall an app to hide it. |
| 14 | First-time setup: **First-time setup checklist** | With the apps installed, complete the foundation settings before any app configuration. Fill in the company details and logo, then the document layout, so every quotation and invoice looks right. Add languages and activate currencies, for example rupees and US dollars for imports. Check the fiscal localization, which for India means the Indian chart of accounts and G S T taxes. It follows the company's country, so set the country before installing Accounting. Finally, invite users with the right access rights for each role, and configure outgoing email in production only. |
| 15 | Key takeaways: **Key takeaways** | To sum up. Decide the edition, hosting, version and database strategy before the first workshop. A database is PostgreSQL data plus the filestore. Back it up as a zip, and restore test databases as copies. Neutralize every copy of production, and promote changes from development, to staging, to production. Install apps with their dependencies in mind, and remember that uninstalling deletes data. Now try the exercises in this course, starting with choosing the right hosting option for each client. |
